## Concrete integration gaps

1. **Admission has to precede journal existence.** The existing broker starts only
   after bootstrap, manifest and fixture import writes. Adding a StorageReserve
   command to its current journal would leave these writes unmetered.
2. **The accounting owner writes too.** Current authority mutations rewrite a
   large JSON row through default SQLite. A SQLite VFS callback that recursively
   asks this same transaction for another durable ticket can deadlock or recurse.
   Exempting authority writes from the cap is not allowed.
3. **Not all bytes pass through WriteQueue.** Queue admission is before media
   mutation, not before each File/Lofty/FFmpeg/SQLite/Python/log write. It cannot
   replace per-write interception or a proved conservative bounded equivalent.
4. **Owners outlive one another.** Receiver recording and launcher status happen
   after broker exit. The original identity needs bounded prepaid recording
   rights, not a new allowance or resurrection of a retired broker.
5. **Errors can be tolerated elsewhere.** Cache/alias failures may be treated as
   optional in desktop logic. A scoped storage denial must independently latch
   the run terminal, so a swallowed I/O error cannot later yield native success.

Read-only inspection of run114's immutable retained registry found a 463,318-byte
final Run JSON, 328,395 compact-JSON bytes of bindings and 497 operations. Each
operation requires reserve, dispatch, arrival and completion, at least 1,988
operation transitions. The database has 228 pages of 4,096 bytes. These facts
establish repeated large state serialization and an important measurement target.
They do **not** measure VFS bytes or prove this workload exceeds 1 GiB. Physical
file size, serialization volume and bytes actually issued at SQLite xWrite must
not be substituted for one another.

## Recommended complete design for review

Use evaluation-scoped admission at the existing owners. Keep WriteQueue, the
coordinator, patch/source validation and scorer. Do not create a second media
writer or resolver. A run-generation-bound storage account must exist before the
receiver's first output file and remain available for bounded terminal recording
after broker retirement. Ordinary desktop instances retain their existing I/O.

The account preallocates finite nonrecursive bookkeeping capacity before payload
admission. Debit conservatively before each actual I/O and sync required durable
admission before acknowledging it. Failed or ambiguous writes keep consumed
tickets. Admission denial closes the existing independent stop latch before any
attempt to write an error/terminal record. Watchdogs never need its storage lock.

Ordinary work can use at most 510 MiB of logical-growth reservations and 1,016 MiB
of application-write reservations. The remaining 2 MiB logical and 8 MiB write
headroom is reserved inside the 512 MiB/1,024 MiB totals for terminal bookkeeping
and at most one bounded failure receipt. Fixed bootstrap/self-accounting capacity
also counts inside those totals. Its own debits cannot create another unbounded
SQLite reservation transaction.

Native files use a metered handle at the shared writer seam, including explicit
offsets, append/growth, truncation and copy. Lofty's `save_to(FileLike)` can use
that handle instead of reopening an unmetered path; actual trait/branch coverage
still needs proof. SQLite connections explicitly select the evaluation VFS before
opening/creating authority, cache, worker and temporary files. xWrite, xTruncate,
xOpen/delete, WAL/checkpoint and writable shared-memory allocation must be covered.
No generic SQL multiplier or periodic directory scan establishes that coverage.

Node/Python preparation and scoring outputs need the same run admission before
their file writes. FFmpeg output and inherited log FDs need metered consumption
or a demonstrated conservative bounded output mechanism; file-size flags alone
do not meter repeated seeks/overwrites. Paths with no supported bounded owner are
denied before opening writable files. Revoke/stop must reject later admissions
without claiming rollback of an already-admitted operation.

First measure authority self-writes through the actual linked SQLite VFS. If
whole-Run rewrites cannot fit, preserve existing command semantics and journal
ownership while storing immutable bindings once and updating bounded state rows.
Do not raise the cap, skip journal accounting or represent a different evaluator
as the same workload. Historical registries remain read-only; no migration or
rewrite of evidence is part of this design.

## Alternatives considered

- **Broker RPC tickets plus WriteQueue/tree monitoring only:** smallest diff but
  incomplete. It misses bootstrap, SQLite internals, external generators, raw
  log FDs and post-broker recording. Reject as an enforcement design.
- **Process-wide interposition or OS quota:** could capture other writes but is
  not an established equivalent on this Mac and does not by itself count logical
  growth plus cumulative SQLite/application bytes. It changes the trust and
  deployment assumptions. No OS change or injection is authorized by this plan.
- **Evaluation-scoped file/VFS integration at existing seams:** recommended.
  Broader than adding counters, but exposes the actual byte boundary and can
  preserve ordinary desktop behavior. Coverage and self-accounting must pass
  review before a six-job fit claim is possible.

## Required red/green and acceptance sequence

Keep failed controls and their exact sources before implementation. Test small,
asymmetric caps first: exact growth and exact write admission; independent +1
rejection before I/O; repeated overwrite; sparse seek growth; shrink/delete and
regrowth with no refunds; two simultaneously present replacement files. Assert
actual bytes and consumed/reserved tickets, not only returned errors.

SQLite controls must use the linked runtime and real DB, rollback journal, WAL,
checkpoint, shared-memory and temp paths. Exercise storage failure, recursion
avoidance and terminal headroom exhaustion. Race workers and tickets at one
authority; errors and missing coverage must retain all 216 requested slots and
prevent later receiver/launcher success.

After those boundaries and independent coverage review pass, freeze all final
source/tool/executable bindings. Run a fresh maintained supervised six-job mock
selection within unchanged 300/600-second scopes, reconcile all requests and
storage tickets with actual writes/readbacks/scoring, audit all 216 slots and
repeat failure/corruption controls. Existing source100/run114 evidence validates
only the previous supervision slice, not new storage admission.

Logical/application/VFS accounting is not device traffic, OS quotas, power-loss
durability or malicious-host containment. Admitted effects after stop can remain
unknown. Existing Clippy108/109 failures, failed gate66 and unexplained runs74/110
remain history, not repaired or promoted by this slice.
