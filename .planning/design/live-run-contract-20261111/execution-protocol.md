# Proposed preparation, execution and retention protocol

**Choose cold coordinator rerun on the same frozen physical media, not continuation or rematerialization.** This specifies design responsibilities for later offline implementation; it is not an executable contract, approval or claim of enforcement. The selected six cold jobs, one conditional Crowd request, zero retries/repairs and zero current live allowance are unchanged.

## One preparation result, one genuine execution observation per job

1. A native supervisor starts before any preparation work. A verifier-owned broker creates a unique preparation ID in its fixed registry with durable requested membership: six `(run, arm, case, profile, cold)` identities, 72 occurrence observations and 216 slots. The broker owns counters from the first counted operation. All inputs, workers and fixture service instances belong to that ID; no user config or original media is read. Approved model/provider/account descriptors are prerequisites for request preparation; current null choices mean this workflow cannot start today.
2. Generate silent seeds and the final 72 destination occurrences before freeze, apply only the declared deterministic profiles, then bind each destination's canonical path, device/inode, full/payload hashes and relevant metadata. Equal paired bytes/metadata must be observed, not assumed from the generator. Physical identities and paths differ between arms and are bound individually. No tagging/candidate application occurs in preparation. Deterministic profile setup and local seed/staging/cache writes are enumerated effects, not read-only activity or scored outcomes.
3. Run plan-only resolution against those final files using per-job preparation-only caches, aliases, worker/temp/review stores and provider-client state. They may change within the declared run root and resource policy; none is transferred to execution. Use identical immutable provider fixture records in both arms, with one registry-wide accounting authority. Preserve lookup, provider completion, no-match, credit/version, local genre/cleanup and circuit rules. A configured capability descriptor supplies the existing configured-client decision without exposing a key or claiming permission to bypass any guard.
4. The coordinator returns an explicit outcome before every candidate/media or review-persistence application path: a hold with no application, a provider-only application plan, a recording-only application plan with exact scope, or a base application plan plus eligible prepared genre request. This includes `country_independent_recordings`, `common_recording_fields`, content-only and normal whole-candidate paths. Every path binds the exact source rows, decision/provenance and reason, branch/scope, selected provider/base candidate, per-file `TrackPatch` omission/null/set semantics, cleanup/lyrics rules, review-intent/evidence transformation and allowed final response-derived fields. Recording-only is not relabelled a whole-album candidate. A hold has an explicit empty mutation plan, not a fabricated candidate or missing event.
5. Any out-of-scope correction/research/acoustic role is an explicit unsupported outcome and terminal failure, never a manufactured expected hold or permission for another request. Natural eligible genre construction is pure and independent of scoring labels. Freeze final owned request bytes/settings and deterministic candidate/patch derivation rules, including ordinary confidence/genre validation. Do not simulate a response to decide the base candidate. Unknown response genre/review fields are parameter slots, never expected labels. No-request outcomes have no model-body binding.
6. Quiesce preparation: all workers/services acknowledge no in-flight operation; broker closes preparation admission, commits final counters and freeze checkpoint, pins exact fixture bytes, descriptor/settings, source/executable/tools, labels, destination identities, result variants and templates. Separate execution stores are empty/predeclared; preparation stores are read-only after freeze. No rematerialization, profile change, source rebinding, cache copying or background writes while awaiting approval. A 15-minute maximum freeze age is proposed; expiry or drift terminates the identity and requires new preparation and approval, never a reset under consumed authority.
7. An independently authenticated approval binds the preparation ID/checkpoint digest, exact choices/limits and all six plans, including zero-call writes and the sole possible paid request. The broker atomically consumes it with an exclusive state transition before any secret lookup, execution candidate application or model send. No new native process can create authority from environment flags, an approval path or its own JSON. Preparation or broker/service crash, unacknowledged freeze or ambiguous consumption makes the identity terminal. A new preparation needs separate approval and does not refund any possible spend.
8. For execution, retain the exact frozen destination files and start **fresh cold** per-job cache/alias/worker/provider/circuit/temp state and service instance registered to the same broker identity. Rerun the maintained coordinator in the fixed job order. Before **any** model dispatch or application branch, compare the actual preparation-result variant, branch/application scope, selected provider/base candidate, deterministic patch/review transformation, actual prewrite physical/content identity and exact request bytes (if any) against the approved plan. Exclude only explicitly enumerated telemetry timestamps/elapsed times and separate store handles from equality; do not ignore candidate/source/provenance differences. Bind stable source fixture IDs/digests instead of dynamic port/store strings, and regenerate final paid request bytes exactly from approved metadata/settings.
9. Any mismatch terminates without reprepare/rebind/repair, even if the new value appears better. Enya's execution hold is a genuine freshly observed decision; preparation's hold is only an approval constraint. If a prepared request becomes a hold or vice versa, stop as decision drift rather than spending or inferring success. All-zero planned requests remain valid and do not require provisioning model credentials. No minimum-wire assertion is allowed.
10. Apply only the approved deterministic base plus the validated response-derived delta through existing WriteQueue. Check per-file dispatch source and authorized destination/patch immediately before writing and actual consumed source bytes under existing queue coordination. Track deliberate atomic replacement as an observed write transition: new postwrite physical identity is recorded, never silently adopted to approve a pending unrelated write. Retain the approved prewrite, proposed final patch/candidate and actual readback independently. An admitted atomic write may finish after stop; remaining rows become unavailable/failed and are not rolled back or presented as a transactional whole-album write. Reopen the isolated worker to inspect permitted review evidence. Ancillary stages are skipped before both album and artist artwork dispatch in all arms; an attempted bypass terminates.
11. Only actual execution observations feed scoring. The adapter identifies each record by arm/cold/source identity, validates available observations against frozen plans and records missing/unvalidated readbacks as unavailable. Failure and agreement may coexist. Incomplete projection never invents native records, uses preparation/base values as readback or infers a hold from unchanged data. Final status publishes atomically after gates; failure grace uses the broker's frozen membership and bounded validated counters, not damaged unbounded exports. Host loss may leave only the predeclared incomplete denominator, not a completed receipt.

The current evaluator's full disabled preparation invocation is **not** this protocol. It applies candidates and has separate services/counters. Implementing plan-only stops and fresh cold rerun comparison is necessary even if factoring the existing resolver is small. Existing `RecordingSource` identity means identical bytes on rematerialized files are not interchangeable after freeze. No such code was changed here.

## One authority includes driver and fixture operations

All counted preparation/execution operations use the broker's typed reservation interface: `(preparation/run ID, stage, arm/job, category, service instance, source/body digest, byte/time upper bounds)`. Provider sends, inventory operations, paid model sends and denied unsupported attempts are distinct categories. The broker transaction verifies current lifecycle/allowance and creates a unique durable operation ID **before** acknowledgment/dispatch; failure to commit denies. Fixture sends/arrivals pair by opaque operation ID without credentials or expected labels. Inventory cannot silently issue an uncounted provider request.

Each fixture-service instance registers its code/manifest/root bindings, stage and run ID on an authenticated channel before binding admission. Service-local arrays are diagnostic mirrors, never authoritative allowance. A replacement for the planned cold transition registers to the existing ID/counters; it cannot import totals, create a fresh ledger or reuse preparation reservations. Close/quiesce the old service with every reservation reconciled before freeze/transition. An unexpected service exit, registration change, orphan arrival, missed journal acknowledgment or counter disagreement terminates. Fixture ingress must acknowledge a durable broker arrival record before releasing a response; unknown delivery remains consumed. An unexpected arrival without reservation is recorded as denied/terminal, never forwarded. Driver local storage/parse/hash reservations also use this ID and finite bounds.

The fixed-registry broker serializes lifecycle/freeze/approval consumption, paid-request and write admissions in durable SQLite transactions. Publication follows durable admission; no counters are reconstructed from child exports after crash. Filesystem writes and network effects cannot be atomic with SQLite: reservations remain consumed across the uncertainty window, and any ambiguous interruption terminates without resume/refund. Read-only recovery may publish a bounded terminal failure from the retained registry; it cannot execute candidate/model/provider operations. Filesystem/SQLite flush semantics, protected registry discovery and target-platform durability remain proof obligations, not assurances from the prose.

Resource admission also needs bounded filesystem/SQLite-VFS write tickets: logical file-length growth and application/VFS write bytes are distinct limits, not physical disk-I/O guarantees. Only one active identity owns registry growth; terminal headroom is reserved before ordinary work. Fixture decoded bytes count repeated deliveries, separate from initial fixture loading. At stop, revoke admissions and terminate/wait for execution groups before receipt-only publication; absent confirmed quiescence the result stays incomplete/unknown. Broker and supervisor cross-monitor, with the surviving native watchdog terminating groups on liveness loss. Stronger containment under both-owner/host failure or uninterruptible I/O is unproven and blocks any such guarantee. Exact units, lease and grace thresholds are in `resource-bounds.md`.

## Broker process owns paid transport, not the evaluated child

In evaluated genre mode the coordinator uses a pure shared request builder and a narrowly typed authenticated IPC operation. The child receives no key, credential supplier, general URL/method/header API, keyed `OpenRouterClient` or unrestricted paid socket. The **broker process** executes the evaluation-scoped `openrouter.rs` transport against the owned approved bytes and owns the deferred credential supplier. It returns bounded validated schema data or stable error codes; endpoint/model/provider/account decisions cannot come from response text. Ordinary desktop transport stays unchanged. The broker must validate the exact candidate/request derivation at admission, not trust a child-supplied `eligible=true`.

Broker-child handles bind registry generation, stage, run/job/arm/role, request digest, executable identity and channel session with freshness/replay protection. The authenticated channel protocol has no general-purpose RPC or credential-export operation. Provisioning its trust root/account descriptor is a separate decision; a Unix socket path alone is not authentication. Keep evaluation initialization on isolated fixture config loading, never the native evaluator's fallback to home config/process secrets. Testing uses fake credentials in a fake broker only; no account lookup/probe is needed to prove negative custody paths.

This relies on trusted reviewed processes and host. It does not stop same-user code injection, debugger/OS secret extraction, admin rollback, arbitrary malicious child code opening its own socket or unrelated spending. Stronger requirements need a separate OS/security boundary, not broader claims about handles. No live/provider billing/privacy assurance is inferred from local transport tests.

## Parsed-value sink inventory and proposed default retention

User acceptance of genres is not approval of this retention policy. Each sink below needs explicit policy binding in a later run approval. Proposed default: local owner-only run root, never committed/shared, no raw paid body retention, delete run-owned value-bearing data within 24 hours of terminal status; quiescent expiry cleanup uses its own bounded local housekeeping authority, never live execution authority. Retaining a selected export longer requires a separately approved duration/scope before running. Cleanup failure is visible and blocks another run until resolved; host-offline deletion timing cannot be guaranteed. No deletion of existing history/media is authorized by this design.

| Sink | Permitted parsed contents | Required disposition |
| --- | --- | --- |
| Broker/child memory and bounded IPC result | Schema-validated genre/confidence or allowlisted error; rejected bounded genre may be carried only to observation projection | Ephemeral; no dumps/debug trace; oversize/control-bearing values fail before application/export, no truncation |
| Frozen provider/base candidate, final candidate/patch and approval preview | Necessary catalog metadata, accepted genre only after response, explicit derivation/review fields | Owner-only plan/readback files inside root; no response-influenced preapproval candidate; delete under approved local policy |
| Disposable tagged media and atomic staging | Accepted genre through approved patches, full provider changes permitted by template | Declared destinations only; never original library; explicit retention/deletion policy covers media/staging, not just JSON |
| Worker/review persistence (worker JSON/database, review marker/journal and reopen evidence) | Accepted genre/model/input digest and necessary inferred-unverified review fields | Project typed evidence before `WorkerStore` serialization; forbid arbitrary report/remote diagnostic strings. Reopen validation required. Include WAL/temp/backups in retention/root/bounds |
| Native observations, final proposal/prewrite/readback and scoring exports | Accepted/rejected bounded genre, confidence/outcome/reason code, actual approved metadata and hashes | Explicit allowed schemas/paths, not every JSON artifact; unavailable/failed still in denominator; owner-only/delete or separately approved retain |
| Provider/fixture inventory, reservation ledger and terminal failure envelope | Exact approved identity IDs, request/response hashes, bounded counters, selectors and stable codes | **No parsed genre or raw model text**, including rejected strings. Terminal receipt may point to approved observation hashes but not echo values |
| General traces, provider attempt diagnostics, reports/events, stdout/stderr, panic messages | Stable allowlisted codes and exact approved telemetry only | Suppress both success and rejection genre/error strings at source; sink filtering alone cannot undo earlier tracing. Reject character-filtered provider strings as identity proof |
| Raw paid HTTP bodies/headers/errors and raw message dump | None by default | Never in ordinary sinks; raw-retention opt-in would require a separate design/policy review, not merely naming an export “scoring” |

Required offline canary test: distinct accepted genre, rejected genre, HTTP error, header and diagnostic identity strings. Inspect disposable tag/readback, candidate, worker reopen, staging/backups, all exports, SQLite/WAL, logs, events/stdout/stderr and failure receipts, including crash/panic paths. The accepted value may reach only declared accepted sinks; rejected value only bounded observation sinks; error/header/diagnostic canaries never general sinks. Expected-label sidecar stays scorer-only, absent from builder, IPC request, broker send bytes, fixture outputs and repair decisions. Send-boundary receipts plus independently constructed full expected requests are required; substring bans alone are insufficient.

## Implementation boundary and remaining feasibility gates

This is a bounded evaluation pipeline, not a generic agent transport, full desktop parity or production approval system. Minimum work still crosses coordinator preparation/application seams, native evaluator initialization/exports, driver/service admission, broker/session+transport, mutation guards and maintained projection. Existing pure resolver/patch/schema logic should be shared; no parallel resolver/writer/scorer. Required scope reductions are cold-only rerun, ancillary stage exclusion, compact inventories and typed projected telemetry. If actual branches cannot freeze deterministic plans without duplicating resolution or weakening source/credit/version rules, stop for design revision rather than change eligibility.

Remaining engineering proofs: all application branches covered; deterministic cold revalidation; cross-process authenticated admission and durable registry; same-ID fixture transition; target-platform supervisor/storage/deadline guarantees; finite workload fit; source-bound request/label separation and complete failure publication. External/user decisions remain exact model/revision/tokenizer/provider, metadata disclosure/retention exceptions/local retention, approval identity/trust provisioning, fee/allowance and overshoot-free guarantee versus quantified residual-risk choice. Neither list is resolved by the other. Nothing here authorizes implementation or any call.
