# Finite resource policy proposed for offline implementation tests

**Every limit below is a proposed rejection threshold, not an implemented control or approved live allowance.** This closes unspecified numeric bounds in the revision-6 design. It does not prove this workload fits. A bound violation terminates the run, preserves requested membership and requires a newly reviewed preparation to change limits; no truncation, auto-increase, retry or fallback is permitted.

## Bound definitions and owners

MiB means 1,048,576 bytes. Counters include preparation and execution, not six new allowances per phase. The independent supervisor starts before the broker/driver; it owns monotonic phase deadlines and limits during synchronous work. The broker is the authoritative journaled counter owner, with its own independent native watchdog for supervisor liveness/deadlines. The service independently meters decoded ingress/egress and fixed record IDs. Children enforce bounded reads before parse and bounded serialization before allocation/output; trusted-child instrumentation is not a sandbox against malicious processes. Offline tests must demonstrate admission, threshold+1 rejection and terminal behavior at actual boundaries before acceptance.

The storage/parse thresholds are initial finite engineering choices, not provider/user approvals or calibrated performance guarantees. No current mock guard is raised. The 8 MiB inventory cap deliberately requires a compact evaluation inventory: immutable fixture record IDs/digests, route/category/timing/byte counters and allowed identity telemetry; model request evidence is a separate preapproved byte binding/send receipt. Do not include raw response bodies or repeated escaped full request bodies. Failure publication uses the already-frozen membership, not an unbounded JSON inventory. This is a necessary diagnostic scope reduction, not permission to hide misses/denials or lose sent-request evidence.

## Storage units, admission and stop ordering

Run storage means the sum of **logical file lengths** of all declared run-owned media, staging, fixture copies, caches, worker/review/temp/export/log files, plus attributable fixed-registry database/WAL/journal growth. It does not mean allocated blocks, free space, device writes or wear. This proposal allows only one active preparation/execution identity in the fixed registry: conservatively charge all registry growth above the frozen pre-run file-length baseline to that identity, including growth shared with lifecycle bookkeeping. Retained historical registry bytes are separately bounded by the registry provisioning policy; absent capacity or concurrent unrelated registry writes deny a new preparation. Sparse files, truncation or deletion never refund cumulative consumption.

Cumulative writes mean bytes issued through application filesystem writes and SQLite VFS writes, counting repeated overwrites, temporary files, journal/WAL and staging copies, not unique payload bytes or physical device traffic. Before each operation, reserve a conservative maximum growth and write-byte ticket from the same broker identity; no refund of unused tickets. Every writable path must go through a bounded writer or evaluation-scoped SQLite VFS that debits the issued ticket before each write/growth. An exhausted/missing ticket rejects before I/O and terminates; an operation whose worst-case ticket cannot be bounded is unsupported. Existing queue guards and post-hoc directory monitoring alone cannot enforce this. The ledger needs pre-reserved self-bookkeeping tickets/capacity so recording a reservation does not recursively request unbounded ledger space. This instrumentation or a demonstrated equivalent is a necessary engineering feasibility gate, not an existing guarantee.

Reserve **2 MiB logical storage and 8 MiB cumulative application-write headroom** upfront for registry terminal bookkeeping and the one ≤64-KiB failure receipt, within—not in addition to—the 512-MiB/1-GiB caps. Ordinary operations cannot consume that headroom. If allocation fails before registration, do not create an executable run; if it is lost after registration, no new receipt is promised. Retained frozen membership and incomplete status remain authoritative; no completion or zero-failure inference is allowed. Registry physical disk exhaustion can still prevent a flush despite logical reservations, so durability/containment needs actual platform proof.

Fixture decoded aggregate means **repeated bytes delivered/read across preparation and execution**, including retries, not unique catalog bodies. Immutable fixture loading/manifest consumption is separately charged to input-consumed bytes and run storage if copied; it does not replace the delivery counter. Reserve the full known uncompressed body length before each response delivery; interrupted/unknown delivery consumes the full ticket. Client readers and service delivery meters must reconcile. These overlapping caps may make some nominal request maxima unreachable; unused count allowance never authorizes more bytes.

At execution deadline/cancellation, broker closes admissions and revokes handles immediately. Admitted atomic operations may have completed before revocation or while termination races; do not claim rollback. If a controlled drain is desired it must finish **inside the original execution deadline**, not grace. At deadline the healthy supervisor requests immediate process-group termination (including native blocking-write threads); no intentional drain is added. The 10-second grace includes waiting for confirmed group exit and bounded terminal publication. If execution cannot be confirmed quiescent, publish no authoritative final receipt: retain incomplete membership and uncertain write/usage states, block another run and surface the cleanup/containment failure. Even confirmed process exit does not prove remote billing cessation or durable filesystem completion; affected observations remain unknown. No successful-final status or unbounded damaged-export parsing occurs in grace.

Supervisor and broker cross-monitor with proposed 250-ms heartbeats and a 1,000-ms lease. The broker checks the absolute monotonic deadline on every admission independently, and an independent native watchdog thread handles expired supervisor lease/deadline even if the Node driver or broker async path is blocked. Liveness loss marks the identity terminal, closes credential/socket and service admission, and the surviving native owner terminates recorded driver/child groups. Broker death is handled by the supervisor; no parent-death cleanup is assumed on macOS. Both native owners/host failure, uninterruptible kernel I/O or failed termination cannot be given a hard cleanup guarantee here. The elapsed containment claim is conditional on a functioning surviving watchdog and target-platform termination behavior; acceptance remains blocked if stronger crash containment is required or the offline proofs fail. Recovered registry state may report failure, never resume/refund.
